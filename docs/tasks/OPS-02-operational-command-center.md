## Problem and user outcome

OPS-01R established `/my-work/{work_item_id}` as the authoritative lifecycle editor, but
My Day still exposes obsolete TASK-07 mutation modals that cannot collect the structured
waiting, blocker, completion, or cancellation data now required by the domain. My Work is
authoritative but remains a flat creation-order list with raw context identifiers.

OPS-02 makes My Day a read-only work-attention surface and My Work the single operational
register for capture, filtering, context display, and lifecycle editing.

## Filter contract

`GET /my-work` accepts only:

- `view`: `current` (default), `history`, or `all`.
- `status`: one existing stored `WorkItemStatus` value.
- `category`: one existing stored `WorkCategory` value.
- `domain`: one existing stored `ResponsibilityDomain` value.
- `context`: `any` (default), `standalone`, or `bid`.
- `bid_id`: required exactly when `context=bid`; forbidden otherwise.
- `attention`: `any` (default), `required`, or `none`.

`status` must agree with `view`: active states cannot be requested from `history`, and
completed/cancelled states cannot be requested from `current`. Unknown or contradictory
filters return an understandable HTTP 422 response. Combined filters are intersections.
There is no public `as_of` parameter; the route supplies the established local application
date while service and pure projection boundaries accept explicit dates for testing.

## Centralized attention and ordering contract

One pure implementation supplies reasons and ordering to both views. Applicable actionable
dates are due date, next-action date, and waiting follow-up date while status is WAITING.
Each work item appears once and retains every applicable reason.

Active ordering tiers are:

1. Blocked.
2. Any actionable date overdue.
3. Any actionable date due today.
4. Other currently-due waiting/follow-up or next-action attention.
5. Upcoming actionable work within the existing seven-day horizon.
6. Remaining scheduled active work.
7. Remaining unscheduled active work.

Within a tier: existing priority rank, earliest relevant actionable date, then stable
work-item ID. My Day keeps its accepted named sections, but entries inside those projections
use this same key; My Work uses the complete key globally. Completed/cancelled records use
stable most-recent-first history presentation and never enter active attention.

## Route and UI behavior

- My Day retains TASK-06 and TASK-09–15 read-only projections and links.
- My Day work rows and history records open `/my-work/{work_item_id}`.
- My Work has `id="quick-capture"`, filter controls, clear filters, active/history/all views,
  resolved context labels, visible reasons, and the existing Quick Capture PRG behavior.
- The editor remains the only HTML mutation surface and retains optimistic concurrency.
- The editor exposes every supported general field, including priority and the existing
  contribution-candidate value. Waiting, blocked, completed, and cancelled controls are
  enabled only when their applicable status is selected so entered data is never silently
  discarded by authoritative state-specific clearing rules.
- The HTML mapping is authoritative end to end: waiting party to `waiting_party_label`,
  expected response/deliverables to `waiting_owed`, follow-up/chase date to `chase_date`,
  blocker description to `blocker_description`, resolution owner to `resolution_owner`,
  completion outcome to `completion_outcome`, and cancellation reason to
  `cancellation_reason`. Legacy `waiting_on` and `blocker_note` remain synchronized only for
  compatibility.
- Back links contain only application-generated, validated My Work filter parameters.
- Existing JSON APIs and routes remain compatible.

## Manual acceptance remediation

Initial OPS-02 browser acceptance failed after waiting values were entered while the item
status remained OPEN. Read-only audit inspection confirmed the route received and audited
OPEN on each affected save. The service correctly enforced existing state-specific clearing,
but the editor had exposed every lifecycle section simultaneously, making the discard silent.
The corrected editor scopes and disables lifecycle inputs by selected status, includes the
previously missing priority and contribution-candidate controls, and renders required fields
for the applicable lifecycle. Production lifecycle validation, persistence schema, atomic
audit writes, and clearing semantics were not weakened or redesigned.
